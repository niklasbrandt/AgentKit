# Factory: the orchestrator loop

You are the orchestrating session. Builders are background subagents. The board ( see the `kanban` skill ) is the source of truth; the repository's AGENTS.md "Collaboration" section and `.factory.json` hold its rules and settings ( column names follow the `lang` preset; this document uses the `en` names ). Helpers: `${CLAUDE_PLUGIN_ROOT}/scripts/` ( `board.sh` ( incl. `stale` ), `watch.sh`, `run.sh`, `verify-report.sh`, `picdiff.mjs`, `mergelock.sh` ).

## Upstream first

A change to a factory-level rule ( board workflow, ticket format, branch rules, merge and review handling, delegation, verify pattern, scripts ) is made in the AgentKit plugin first: templates, skills, scripts, a `version` bump in `.claude-plugin/plugin.json` and `marketplace.json`, an entry in `CHANGELOG.md` copied into the README's Changelog section, and, for a significant change ( a skill, script, flag, config key, column or rule added, removed or renamed; a changed workflow ), the README sections it touches, all in one commit ( README, "Maintaining AgentKit" ). Then `scripts/init.sh` is re-run in every repository that uses the plugin. Repo-specific content ( ports, umbrella branches, tools, domain rules ) stays in the repository, outside the `<!-- factory:... -->` markers. Never edit the text between the markers in a repository.

## 0. Kickoff ( once )

1. **Read `STATE.md` first** ( repo root, if a previous session left one ), then `board.sh state` ( a draft of the sheet from the board ). `git fetch`, read `AGENTS.md`, `CLAUDE.md`, `.factory.json`, and the plan or epic the owner named. Read the board: `board.sh list`. Check `ListAgents` and the transcripts of peer sessions ( `~/.claude/projects/<project>/<session>.jsonl`, read-only; read the end to tell finished from waiting for an answer ) so you never duplicate a session the owner already opened.
2. **Assumptions over questions.** Open points are answered from the repo first ( the plan, the tickets, rulings / canon, the owner's earlier decisions and art direction, the code ). What the repo does not answer, you assume, in line with that direction, and have it written under **Assumptions** in the ticket ( one line each: the assumption, why, what it touches ). Ask the owner only when an assumption would be irreversible or expensive to undo ( money, accounts, deleting their work, a canon-level fact many things build on ), and then **all questions at once, in one message, now**. A wrong assumption costs a change, a stalled ticket costs a night.
3. **Ask for a hands-off list** in the same message: areas the owner wants to decide in person before any agent touches them. Record it and keep every builder out of them, drafts included.
4. **Write `STATE.md`** at the repository root ( gitignored by init, local to the machine ) and **rewrite it, not append, at every hand-back, every spawn and every owner decision**. Long sessions lose what is not in a ticket: who runs now, on what, where, what waits for what, which limits you set yourself. Fixed sections, in this order:
   - `## Running`: a line `Shift lead: <agent / none>`, then a table: ticket, title, agent kind / model / effort, worktree, ports, started, last progress ( time of the agent's last commit, note or message ), phase ( build / finish / fix ).
   - `## Waiting`: ticket → what it waits for.
   - `## Queue`: the next tickets in the owner's order, with the reason if blocked ( "A and B both edit file X: B after A" ).
   - `## Owner decisions open`: one line each, with your recommendation.
   - `## Limits`: builder cap, headless-browser cap, port map, locked files, the owner's ports ( never touched ).
   - `## Last hand-backs`: the last 10: ticket, sha, deployed entry file, date.
   - `## Notes`: rules you set yourself and incidents, dated.

   `board.sh state` prints the parts the board knows under the same headings; paste it and fill in agents, ports and worktrees. Never keep this only in the chat: the conversation can be compacted at any time, and everything else lives in the tickets and on the branches.
5. Keep the machine awake while work runs: on macOS start `caffeinate -dimsu` in the background ( note its PID, stop it when the work is finished or the session ends ).
6. Start the watcher ( below ).

## 1. The loop

Repeat until Ready and Backlog hold nothing you may take ( or the owner's scope is done ):

1. **Pick:** the top of Ready, else the top of Backlog ( `board.sh next` ). Never reorder. Skip what needs the owner ( below ), blocked tickets stay in Backlog. If a ticket is vague, specify it ( short ticket, `kanban` template ) and move it to Ready first. Tickets that edit the same files run in sequence; `STATE.md` says which ( Limits: locked files ). **Before you create a ticket, search for overlap and extend an existing one** rather than opening a twin. **Cut work packages:** when several Ready tickets share files or an order ( the same subsystem, a chain of fixes on one file ), propose one package ticket per topic to the owner ( sub-issues, order, locked files ), and once approved run it as one builder on one branch with one verify and merge ( and one deploy per batch, by you ); each sub-issue still gets its own checks, assumptions, numbers and merged line ( `kanban` skill, "Work packages" ). The board then shows topics, which is what the owner sorts.
2. **Prepare:** spawn only while `capacity.sh` recommends more `agents` than are running ( section 5c ). When the owner wants more parallel work, fill up to that number: its `queue` measure ( how long guarded `run.sh` starts queued in the last 30 minutes ) lowers it as soon as more agents would only add waiting, so the factory as a whole does not get slower. A repository's own copy of `run.sh` must log its queue time the same way ( `FACTORY_WAITLOG` ), or the measure stays blind. `board.sh move <n> "In Progress (Agent)"`. Branch `<type>/<id>-<slug>` from `main`, or from the umbrella branch the ticket or epic names. One worktree per ticket: `git worktree add ../<repo>-<id> -b <branch> <base>`, then the repo's install step in it. Pick a port block no other running agent uses ( the app's default or `--port <n>` ); never the owner's own dev server port.
3. **Delegate:** start a **background subagent** ( Agent tool, `run_in_background` ) per ticket. Several tickets run in parallel when they do not touch the same files; stacked ones run in order. Give each agent the ticket text, the branch, the worktree path, its ports, the verify command, the list of peer ports and worktrees, and these rules: assume and record under **Assumptions** in the ticket instead of asking ( ask only for what is irreversible or expensive to undo, see kickoff ), commit early and often on the branch, push it, heartbeat ( commit WIP or post a one-line progress note at least every 30 minutes; when waiting, say in one line on what and for how long; never wait more than 20 minutes on a lock or another agent without reporting ), never touch other worktrees, stop only processes you started ( by PID ), headless browsers only through the repo's launcher under `run.sh`, muted, windowless and without audio ( section 5b ), merge-test-push in one `&&` chain, a clean tree after a build, no generated data in git, no deploy step ( the orchestrator deploys, once per batch; say in the hand-over if you need a deployed state to test ), never move cards to Done, report with what was done, what was checked with numbers, what is open, and every assumption.
   - **Model and reasoning effort per ticket ( set `effort` explicitly ):**
     - Opus, `high`: large tickets and milestones, and every ticket that creates or reshapes 3D geometry ( the default for builders ).
     - Opus, `xhigh`: foundations that later work builds on ( a new API, coordinate maths, a data model ).
     - Sonnet, `medium`: small, mechanical, well-specified tickets without geometry. **Sonnet never generates 3D geometry** ( meshes and the code that builds them ): it checks, tabulates, does UI, tooling, bookkeeping, docs and merges.
     - The tier above Opus ( where the account has one ): **never on your own judgement.** Only when the owner asks for it by name, or when a ticket has gone through several rejected revisions on Opus without a result the owner accepts. Then only for the steps that need judgement of form or design, and resume the same agent with a message instead of starting a new one ( it keeps what it understood ).
     - **Cascade inside a ticket:** split it by what each part needs and run the parts one after another: the top tier ( if granted ) for the form-critical steps, Opus for geometry and hard technical steps, Sonnet for the rest without geometry. Each part ends with a short hand-over file on the branch for the next.
     - **Effort is a second dial, set on every spawn ( the Agent tool's `effort`; never leave it to the default ):** `low` for deployers, merges, bookkeeping and lookups; `medium` for mechanical tickets and docs that only restate; `high` for builders, debugging with an unknown cause and analysis that needs judgement; `xhigh` only for foundations and for a fix that already failed once at `high`. Pick model and effort together from what the work needs, not from the ticket's size: Sonnet `high` for a hard non-geometry bug hunt is often better value than Opus `medium`.
     - **Re-route when the scope changes.** Model and effort are fixed when an agent starts; a message ( SendMessage ) keeps both. So resume by message only while the next step needs the same model and effort. When it does not ( a Sonnet bug fix turns out to need new geometry, an Opus build is done and what is left is verify, captures and merge, a docs analysis turns into a foundation decision, a fix failed at `high` ), let the agent stop at a hand-over file on its branch ( what is done, what is open, decisions, numbers ) and start the next part as a new agent with the model and effort that part needs, given that file and the branch. Note the switch and its reason in `STATE.md` ( Running: model / effort column ) and in the ticket. Reason: an agent kept on its starting model after its scope changed either did geometry on a model too weak for it or spent the strong model's tokens on bookkeeping.
     - Name the model and effort when you show the owner a result.
     - A plan may set it per milestone; that wins. You ( the orchestrator ) run at `high` and raise it only for a real judgement call: reviewing an API, a milestone that missed its target.
4. **Review** when the agent reports: read the diff against the ticket's checks ( footprint: files, sizes, nothing generated or binary that does not belong ), run the repo's verify command in the agent's worktree ( `verify-report.sh`, or the commands in `.factory.json` ), look at screenshots or output for visible changes ( `picdiff.mjs` before / after ). A visual fix holds under every condition the app renders, not only the one in the report: the same pose at each time of day and weather it has ( noon, sunset, twilight, night, dawn, overcast, rain, fog ); a sheet with one light only goes back ( reason: a haze fix checked at noon only came back at dusk and the owner had to report it twice ). Read the builder's **Assumptions**: check each fits the plan and art direction ( send it back if not ), make sure they are in the ticket. Then post the review on the ticket as a comment ( "Review (Orchestrator)": what was checked with numbers, what the owner has to judge, side effects such as tools the builder installed on the machine ) and list the assumptions in your report to the owner so they can correct them. Flaws you find beyond the ticket's scope become new short tickets, not side fixes. Send fixes back to the same agent ( SendMessage ) when they need the same model and effort, else start a follow-up with the fitting ones ( section 3, Re-route ); do not merge on a FAIL.
5. **Merge:** merge `main` ( or the umbrella branch ) into the ticket branch first, run the verify command on the merged tree ( smoke test ), then merge into `main` or the umbrella branch and push, in one `&&` chain. Merge when no other agent is in the middle of a step in the target's worktree; say in the ticket if you merged into a worktree someone works in. No force-push, no rebase of pushed branches. Builders never deploy. Batch cycle: merge -> deployer agent: batch verify on the tip, build, one deploy. When the batch is merged and the repository deploys ( `.factory.json` `deploy` or the plan says so ), you decide that it is time and start one **deployer agent** ( the cheapest model, Haiku or Sonnet `low`; never two at once ). Under the merge lock ( `mergelock.sh`, the serialisation: no merge lands while it runs ) it runs the verify command on exactly the tip of `main` ( or the umbrella ), builds, deploys that tip once through the repository's single deploy script ( it gates on generated data present and the served page read back naming this build's entry file ) and returns one line: sha, entry file, read-back result. A failed verify or read-back is its whole report; it fixes nothing. You write the line into `STATE.md` ( Last hand-backs ). Reason for the agent: the deploy's logs and waiting cost the orchestrator's context and tokens for a mechanical step. Reason: builders that each deployed after their own merge once shipped a build lacking generated files another merge had just introduced, and the live page broke; others deployed intermediate umbrella states within minutes.
   - **No half states on the integration branch:** a ticket built in phases ( canon or data first, code second ) is merged when the integration branch stays consistent after it; a phase that leaves tests red or the app half converted waits on its branch for the next phase. Reason: the owner's preview and every other builder's merge base would show a world half moved.
   - **Owner preview of the integration tip:** one dev server of `main` ( or the umbrella ) on a fixed port of yours, started once, `git pull` after every merge so the owner always sees what is merged; its port in `STATE.md` ( Limits ) so no probe uses it.
6. **Hand back:** `board.sh merged <n> <sha> <branch>` ( line, label `merged`, assignee ), then `board.sh move <n> "In Review"`, then `worktrees.sh --apply` ( the merged worktree goes; see the kanban skill ). At every rewrite of `STATE.md` run `worktrees.sh` and act on its warning: more worktrees than `agentsMax` + 2 means finished work was left lying. Paste the verify report into the ticket ( `verify-report.sh | gh issue comment <n> --body-file -` ). Changes the owner asks for later go through the same branch and are merged again; move the card back to In Progress (Agent) first, with a "Changed after review" section.
7. **Next:** start the next tickets yourself and rewrite `STATE.md`. Do not wait for the owner between tickets of an approved plan.

Never run two performance measurements ( frame times, benchmarks, profilers ) at once: they distort each other. Queue them, or use a lock file. Functional checks may run in parallel on separate ports.

**Reports to the owner.** Whatever covers more than one ticket ( a hand-back round, a batch summary, the queue ) is a bullet list, one bullet per ticket: `**#31 ( Title )**`, one sentence on what the ticket does for the owner ( a title alone explains nothing to someone who did not read the ticket ), then its state and what is open. Never two tickets in one paragraph. Cross-ticket facts ( capacity, the deployed entry file ) are one closing paragraph. Every report ends with the next step as a question ( yes / no, or a / b / c, the recommendation first ) and, when nothing is left to do until an agent reports, with the line that you stand by until the agents report. The shift lead's summaries follow the same form.

## 2. What needs the owner

Stop and ask only for these, and keep working on everything else:

- moving a card to **Done** ( never do it; never touch a card already there )
- money, accounts, credentials, server settings, hardware, external assets ( such a ticket goes to In Progress (Human), assigned to them )
- canon-like world facts: anything that decides what is true in the product's world, story or domain ( the repo says where its canon lives )
- hosting of large generated data ( where gigabytes of tiles, renders or datasets live; the builder keeps them out of git and local )
- anything on a server beyond uploading the built site and static assets: **no executable server-side files ever** ( no PHP, CGI, shell scripts, handlers in `.htaccess` ), no server configuration, no new credentials or keys; free space and quotas come from the FTP server's own commands, from the owner's control panel, or are reported as unknown
- removing what they specified, deleting a sub-ticket, reordering the Backlog
- anything on the hands-off list
- decisions only they can make ( taste, legal, naming of a public thing ), but only where an assumption would be irreversible or expensive to undo; otherwise assume, record under **Assumptions** and keep going

## 3. The watcher

Wait with the **Monitor** tool, never by polling in a loop:

```
Monitor( command: "${CLAUDE_PLUGIN_ROOT}/scripts/watch.sh 31 32 33", description: "board + sessions", timeout_ms: 1800000 )
```

`watch.sh` prints one line per change: a ticket's column, assignees or labels changed, a session transcript appeared, went quiet ( no write for 5 minutes: finished or waiting for an answer ) or became active. Env: `INTERVAL` ( 30 s ), `QUIET` ( 300 s ). A card the owner moves ( back from In Review with a change request, or to Done ) shows up there; react to it. A Monitor expires after at most 30 minutes: re-arm it on the expiry notice.

## 4. Long sessions: limits, compaction, session end

- **Usage limits.** When the account's usage window is exhausted ( HTTP 429 ), builders stop where they are; their state is committed on their branch. Do not restart them: once the window has reset, send each a message ( SendMessage ) to continue. Deploy and merge what is finished before the window runs out.
- **Compaction.** The conversation may be summarised at any time. Keep nothing only in the chat: `STATE.md`, the tickets ( review comments, assumptions, merged lines ) and the branches hold the state. `ListAgents` returns the builders' handles afterwards. Compact between reviews, not in the middle of one.
- **Subagents end with the session.** Background subagents die when the session that started them ends. Work that must outlive it ( hours of builds, a night run ) goes into a **separate session** ( `claude -p "<prompt>"` in its worktree, under `caffeinate` ), with its transcript watched through `watch.sh`. Before ending, make sure nothing is left half-merged: every agent's work is committed and pushed, every card is in the right column, `caffeinate` is stopped, dev servers you started are stopped by PID.

## 4a. Long sessions: renewal without the owner

Never ask the owner to start a new session; the factory renews itself.

- **Compaction is automatic.** `STATE.md` and the board make it lossless: after a summary, re-read `STATE.md`, run `board.sh state`, and simply continue.
- **Shift leads.** Per batch of tickets, start one long-lived orchestrator subagent, the shift lead. It reads `STATE.md`, starts and reviews the builders, merges, and hands back only decisions and short summaries. When its context grows large it rewrites `STATE.md` and reports; you start the next shift lead. The root session stays thin and permanent, and `STATE.md` names the current shift lead under Running.
- **A scheduled routine** that rehydrates a fresh run from `STATE.md` is optional, and only where the environment allows it.

## 4b. Visible changes: the neighbour test

A fix that removes the flaw a reviewer flagged can still add a new one: the element is right in isolation and looks nothing like what stands next to it. So for every visible change ( UI, geometry, a page, a component ):

- **Build from the existing set.** The same window type, control style, spacing, materials and fonts as the neighbours; never the builder's own variant. No second type of an element where one type exists.
- **Builder hands over context captures:** the new element side by side with its nearest existing neighbours of the same kind, same distance / scale, same state ( day and night, hover and rest ), plus the overview views the domain demands ( 3D: usual distance, from below, from above, close ), and a line on what differs and why that is intended.
- **Reviewer never accepts on the absence of the previous flaw.** Acceptance is "it looks as if it had always been there", judged against the neighbours; the review comment names the neighbour comparison with the capture paths.
- **Automate where the repo can** ( a neighbour crop sheet, an element-type histogram, a material scale check ) and put it in the verify command; until then make the sheet by hand.
- The builder prompt asks for the captures and names the neighbours ( delegation template ).

## 4c. Stalled agents: the watchdog

An agent that stands still without saying so is the orchestrator's problem, never the owner's. Reason: a finishing agent once stood for two hours with no commit, no running process and no message, and the owner noticed first. Builders carry the heartbeat ( delegation rules in section 1: a commit or a one-line progress note at least every 30 minutes; a one-line "waiting on X for Y" instead of silence; never more than 20 minutes on a lock or another agent without reporting ). You watch it:

1. **Every 30 minutes** run `board.sh stale` and `capacity.sh` ( section 5c ) ( per worktree: minutes since the last commit, minutes since the last change of any file, a process inside or not, verdict `STALE` when both ages exceed 45 minutes and nothing runs; the merge lock with its age, a lock older than 30 minutes with no `mergelock.sh` process is a stale lock: remove it ) and update the `Last progress` column of `STATE.md`. Arm a Monitor for the 30-minute cadence; a transcript that went quiet ( `watch.sh` ) is the same signal from the other side.
2. **No progress for 45 minutes** ( no commit, no file change, no note, no process ): one ping ( SendMessage ) with a precise next step ( "run X, then commit", "the lock is free, merge now" ), never a vague "status?". Note the ping and its time in `STATE.md` ( Waiting ).
3. **No progress 20 minutes after the ping:** stop the agent ( TaskStop ), write its state into `STATE.md` ( last commit, what was left, what it waited on ), and spawn a successor on the **same worktree** and branch from the state sheet: the worktree holds the committed work, so nothing is rebuilt. Uncommitted changes are left in place; the successor's first step is to read `git status` and commit what is sound.
4. **Never wait on an agent for more than an hour**, whatever it reports. An agent that says it waits on another agent is checked against that agent's row in `STATE.md`.
5. A legitimately long step ( a full build, a capture set ) shows as a running process in `board.sh stale`; it is not stalled, but the builder still posts its one line saying what it waits on.

## 5. Budget: the usage window

The account's usage limit is a token budget per 5-hour window, shared by the orchestrator and every builder. Parallelism changes when the window runs out, not how much gets built per window; the model mix and the tokens per ticket do.

- **The weekly limit comes first.** Beside the 5-hour window the plan has a weekly limit, and a full board of builders can eat most of it in a day. It cannot be read from inside a session: ask the owner for the weekly usage before a batch and at the start of each day, write it into `STATE.md` with the days left, and plan against it. Roughly: usage ahead of the week's pace by more than 20 points, or above 70 %: two builders at most, no top tier, Sonnet wherever the rules allow it. Above 85 %: wind down. Builders close out with a hand-over instead of iterating, what is finished is merged, and nothing new starts without the owner's yes.
- **`agentsMax` is a hard cap, not a target.** Count every running subagent against it ( builders, finishers, the deployer ), also when the owner says "full speed". More than the cap only with a number from the owner.
- **Automated "still waiting" notifications** from builders cost an orchestrator turn each: answer them in one line and do nothing else.
- **Six builders at once** is the budget's upper bound ( `agentsMax`, default 6; not eight ): six last the whole window, eight empty it in about three hours and then everything idles until the reset. How many run right now is what the machine allows ( `capacity.sh`, section 5c ).
- **Model mix:** Opus tokens weigh several times Sonnet tokens against the window. Sonnet `medium` for mechanical tickets ( a bug with a known cause, sounds, small UI, bookkeeping, docs ); Opus `high` for milestones and anything with judgement; `xhigh` only for foundations. Roughly a third of a board's tickets are Sonnet work.
- **The orchestrator's own share is small** next to a builder ( a builder spends 200k–700k tokens on a ticket ); do not downgrade the orchestrator to save budget.
- **Trim the builder prompts:** quick verify by default, the full verify only when sky, terrain or post-processing is touched; capture sets only where the acceptance names them; no re-measuring performance on a loaded machine ( record "not provable, machine loaded" and queue a quiet-machine re-measure instead ).
- **When the window runs out** every builder stops with its state committed; resume each with a message after the reset ( section 4 ). Merge, and deploy once, what is finished before the window runs out, not after.
- Before a night run, start the big tickets first so they get the longest uninterrupted stretch.
- **No new builder in the last hour of a window**: it would pay its read-in twice.

- **GitHub's GraphQL quota** ( 5,000 points an hour for the whole account ) is shared by every agent: `board.sh` waits for its reset by itself; repository tooling that runs on every build or dev start ( release notes, dashboards ) reads issues through REST in one listing, caches the result for minutes, and never asks once per card. Reason: release notes that fetched each Done card per build emptied the quota within the hour and froze the board for everyone.
- **Shell loops in the orchestrator run in bash** ( `bash -c '...'` ): zsh does not split an unquoted `$var` into words, so `set -- $spec` or `for x in $list` silently pass one long word. Reason: a worktree loop created a folder with a space in its path and a local branch named `origin/<umbrella>`, which made every later `origin/<umbrella>` ambiguous; `worktrees.sh` now warns about both.

## 5a. Squeezing the budget: two phases, locks, reads

- **Two-phase builders.** A ticket is built by an Opus builder and finished by a Sonnet finisher. The builder designs, implements, runs the fast checks and stops when its own acceptance passes, with a short handover in the ticket: branch, what changed, what to verify, where the captures go. The finisher ( Sonnet `medium` ) takes the branch and the acceptance list, runs the full verify, takes the captures, writes the ticket ( checks, numbers, assumptions as the builder left them ), merges with the lock and reports ( no deploy: that is the orchestrator's step ). About a third of a ticket's tokens are that tail, and Opus tokens weigh several times Sonnet's. Skip the split only for tickets under an hour.
- **Merge lock.** One local lock around merge → verify → push ( `scripts/mergelock.sh <cmd>` in the plugin, or the repo's own ): a builder waits for the lock instead of re-verifying because the umbrella moved under it. Waiting is free; a second verify is not.
- **Read by range, never whole.** Files over ~40 KB are read with grep and line ranges; a generated module map ( function names and line ranges per file, refreshed by verify ) tells a builder where to look. Reading a 300 KB file whole costs 80k tokens, and builders used to do it several times a ticket.
- **Trim tool output.** Tail and summarise logs; verify prints a one-screen summary; capture lists go to a file, not the transcript.
- **Context packs, not plans.** The prompt names the exact plan sections and done lines a ticket needs; a builder does not read a whole plan.

## 5b. Headless checks never touch the owner's machine

- **Muted and windowless:** `headless: 'new'`, `--mute-audio`, no `bringToFront` or target activation, no window position or focus calls, no OS input tools. A builder that steals focus or the mouse interrupts the owner.
- **Every headless process that could open an audio device is silent too:** Blender with `-noaudio`, ffmpeg without playback, Python / Node audio libraries off. Reason: a Blender run without the flag opened CoreAudio on every start and the owner heard the device switch while the browsers were already muted.
- **One central launcher per repository** sets these flags, runs under `run.sh`, and opens the app with its no-audio flag ( the repository names it, e.g. `?noAudio` ): the app creates no audio context at all, because even a muted headless browser that opens one makes the operating system reconfigure the shared output device, and the owner hears pops.
- **Never the owner's installed browser bundle:** headless checks never run it ( on macOS the app bundle under /Applications ): the operating system then treats every headless instance as 'the browser is running', so the owner's own browser will not start, and focus, keyboard and the audio session are routed to the wrong process. Use a separate browser build ( Chrome for Testing, installed into a cache folder by a repo script ) through the repo's single launcher, with an env override for the path.
- **A machine-wide cap:** at most the `headless` that `capacity.sh` recommends right now ( measured; upper bound `headlessMax`, `.factory.json`, default 4, `headlessCap` read as its alias ) headless browsers at once, across all builders; they share the GPU with the owner's browser. `run.sh` re-measures while it waits; `HEADLESS_CAP` overrides it. `STATE.md` shows it under Limits.
- **Load guard:** no new headless run while the 1-minute load average is above the core count. `run.sh` waits for both ( up to `FACTORY_LOAD_WAIT` seconds, default 600, one line when it waits ), then runs.
- The owner's own dev server and browser are never touched.

## 5c. Dynamic capacity

How many agents and headless browsers run is measured, not guessed. `scripts/capacity.sh` reads the machine's bottlenecks ( 1-minute load against the cores, thermal limit, memory pressure and swap, GPU utilisation, headless browsers already running, disk MB/s ) and the owner's activity, and recommends `agents` and `headless` for right now, between 1 and the maxima of `.factory.json` ( `agentsMax`, default 6; `headlessMax`, default 4 ). `--json` gives `{ agents, headless, free_headless, owner, reasons, measures }`. Reason: fixed caps were too high on a loaded machine, so the owner's own work stuttered, and too low at night, when the machine stood idle.

1. **Before every spawn** run `capacity.sh --json` and spawn only while its `agents` is above the number of agents running ( `STATE.md`, Running; shift lead and finishers count ). A drop never stops a running agent; it only holds back the next one.
2. **Every 30 minutes**, together with `board.sh stale` ( 4c ), run it again and write the result into `STATE.md` ( Limits: Capacity ( last measured ) ); `board.sh state` prints it.
3. **`free_headless` 0 pauses browser work, not agents.** Builders keep building, testing and type-checking; captures and visual checks wait ( `run.sh` waits by itself, up to `FACTORY_LOAD_WAIT` ). A builder prompt says so.
4. **The owner's use of the machine comes first.** Last input less than `idleMinutes` ( default 10 ) ago, or an established connection on one of `ownerPorts` ( the owner's own dev servers ), means **active**: headroom is reserved, agents −2, headless −2, GPU threshold 60 % instead of 70 %. **Idle** from `idleMinutes` on: no reservation, the hardware limits alone decide. **AFK** from `afkMinutes` ( default 30 ) on: up to `agentsMax` + 2 while load and GPU allow, so the factory runs flat out while nobody uses the machine, overnight included.
5. **The owner's word overrides the measurement.** When the owner says the machine is slow, halve the recommendation ( agents and headless, rounded down, at least 1 ) and note it in `STATE.md` ( Limits and Notes ) until the owner says otherwise; it holds through idle and AFK.

## 6. Checklist per ticket

`capacity.sh` agents above the running count -> card in In Progress (Agent) -> branch + worktree + install + ports -> subagent with model and effort -> verify green ( headless cap respected ) -> visible change: neighbour comparison captured and judged -> assumptions read and surfaced -> merged tree verified -> merged and pushed in one chain -> `merged` line + label -> review comment on the ticket -> In Review -> `STATE.md` rewritten -> next ticket. Every 30 minutes meanwhile: `board.sh stale` and `capacity.sh`, `Last progress` updated, ping at 45 minutes, replace at 65 ( section 4c ). Per batch, after the merges: the orchestrator triggers one deployer agent ( cheapest model, under the merge lock ) -> batch verify on the tip, build, gated deploy, read back -> its one line ( sha, entry file, read-back ) in `STATE.md`.
